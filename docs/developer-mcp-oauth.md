# Developer MCP authorization

This source implements browser consent for the existing paid developer MCP resource. It does not deploy an issuer, register a live client, activate billing, configure a provider, or approve commercial terms. Consumer Supabase OAuth consent and legacy consumer Project MCP routes are separate and unchanged.

The operator must set an exact HTTPS origin in `KOVA_MCP_ISSUER` (no trailing slash or path), provide the existing independent `DEVELOPER_KEY_PEPPER`, and explicitly enable `KOVA_MCP_OAUTH_ENABLED`, `KOVA_DEVELOPER_API_ENABLED` and `KOVA_DEVELOPER_BILLING_ENABLED`. The ordinary approved pricing, funding, provider and deployment gates still apply. No OAuth token can bypass them. `KOVA_MCP_DYNAMIC_REGISTRATION_ENABLED` defaults off and must be reviewed independently before exposing public registration.

| Surface                                   | Contract                                                                                                                                                                                              |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/oauth-authorization-server` | Exact configured issuer, authorization/token/revocation endpoints, S256, supported scopes; registration advertised only when enabled.                                                                 |
| `/.well-known/oauth-protected-resource`   | Exact `${issuer}/mcp` audience and the same authorization server. Disabled issuers return 404.                                                                                                        |
| `GET /oauth/mcp/authorize`                | Authorization code only, S256 only, exact registered redirect, bounded state, explicit scope and exact resource. The first redirect is to the issuer's consent page.                                  |
| `/developers/authorize?request_id=…`      | Signed-in owner reviews client ID/name, callback, resource, an owned developer project, permissions and explicit per-request/day/month/concurrency limits. An additional review checkbox is required. |
| `POST /oauth/mcp/token`                   | Public-client form request with client ID, exact resource and code+verifier+exact callback, or a rotating refresh token.                                                                              |
| `POST /oauth/mcp/register`                | Optional dynamic registration: bounded public-client metadata, no client secret, URLs never fetched. Ten registrations per IP per hour plus database registry limits.                                 |
| `POST /oauth/mcp/revoke`                  | Revoke by exact client and credential; unknown credentials return success without exposing their existence.                                                                                           |
| `/developers/connections`                 | Verified owner preregistration, active client IDs, deterministically paginated grants, current currency/limits, grant revocation and client retirement. Registration grants no account access.        |
| `POST /mcp`                               | Ordinary scoped developer API key or dedicated OAuth bearer access token. OAuth tokens are accepted only for this resource. Browser origins must match a registered callback origin.                  |

Public web callbacks use canonical HTTPS URLs without userinfo or fragments. Native clients may preregister an exact HTTP loopback IP callback (`127.0.0.1` or `[::1]`) with an explicit port. There are no wildcard redirects, DNS localhost aliases, dynamically accepted ports, metadata-URL fetches or provider credentials. Existing callback query pairs are preserved; OAuth response `state`, `iss` and code/error cannot replace a preregistered field.

Scopes are `chat`, `image_generation`, `embeddings` and `files`. The files scope means **read and manage private developer text files in this developer project**, not consumer Projects or Library access. Integrate the canonical developer-files MCP CRUD/identity-helper package together with this package; its RPC rechecks the same ordinary backing key, current files capability, project, owner and deletion fence. Tool selection and generation file references remain scope-gated.

Consent binds the immutable request hash, selected project, scope subset and exact spending choices to a canonical review hash. The server compares those bytes to the displayed request, and the database atomically rechecks current ownership, verified non-banned Auth identity, account deletion and Lockdown state, active client, current project/account limits and the 100 non-revoked-key account cap. A grant receives an ordinary metering key whose random digest is never exposed. Revoking a grant or client disables that key under the canonical developer billing lock; provider dispatch therefore rejects a revocation that happens after quote or billing admission.

Codes last two minutes and are consumed once. Opaque access tokens last at most 15 minutes. Clients registered for refresh receive rotating refresh tokens with an absolute 30-day grant deadline, further limited by active registration. Code-only clients receive no refresh token. Replaying an already consumed code or refresh token durably revokes the entire grant. Wrong PKCE, redirect, client or resource does not consume a valid code. A lost successful code/token response requires starting a new consent flow; the server never reconstructs stored plaintext credentials. Owners can revoke unused grants, and abandoned unactivated grants are retired before admitting a later grant after their code deadline.

No plaintext token/code is stored. Digests are HMAC-SHA-256 with the `mcp-oauth-v1` domain, distinct from ordinary API-key credentials. Client registration metadata is immutable. Deleting its registering Auth owner retires the client and all dependent grants; deleting a grant owner cascades private codes/tokens/requests. Trigger helpers have an empty search path and narrowly defined definer behavior so Auth deletion needs no unrelated table grants. Current owner status is read through a private helper; production service role does not need `SELECT auth.users`.

Storage is bounded: at most 1,000 active clients and 10,000 retained client rows globally, 20 active registered clients per owner, 5,000 active/10,000 retained requests, 1,000 retained grants per owner and 50,000 globally, and 6,000 token rows per grant. Admission sweeps bounded batches of expired requests and unreferenced retired registrations; owner consent sweeps terminal grants older than 30 days. Consumed refresh evidence remains through the bounded grant lifecycle for replay detection. Public registration metadata referenced by another owner's connection history may remain until those references expire or are removed. These implementation windows do not assert an approved legal or financial retention policy.

Owner export projections are `mcp_oauth_grant_export_rows` and `mcp_oauth_client_export_rows`, both keyed by `owner_id` with deterministic `id` order. They include approved scopes, current spending limits/currency, public registration metadata and lifecycle times; no secret digests, tokens, codes or PKCE challenges. Both are registered with the cumulative bounded account exporter.

The browser captures the owner and sign-in token before each bounded request, sends `X-Kova-Expected-User`, uses abort/deadline and byte-limited reads, and unmounts private consent on account/request changes or device privacy reset. A late response cannot redirect a new owner or revive a cleared consent form. The response destination is checked against the reviewed callback before navigation. Existing page CSP/frame restrictions also apply.

Verification uses the actual migration and canonical billing SQL under service/Auth roles, actual HTTP handler-to-SQL flows with local Auth/rate fixtures, and Chromium consent interactions. No test represents a live provider, deployed OAuth issuer, payment proof or sandbox infrastructure acceptance. References: [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [OAuth security best practice](https://www.rfc-editor.org/rfc/rfc9700.html), [dynamic client registration](https://www.rfc-editor.org/rfc/rfc7591.html).
