# Versioned developer ingress

The source adds `/api/v1/models`, `/api/v1/quotes`, `/api/v1/responses`, `/api/v1/images`, `/api/v1/embeddings`, a scoped bearer-key `/mcp`, and `/developers/console`. Both `KOVA_DEVELOPER_API_ENABLED` and `KOVA_DEVELOPER_BILLING_ENABLED` must be explicitly true for API or MCP execution. No activation, prices, funded accounts, credentials, provider requests or payment calls are made by this change.

`DEVELOPER_KEY_PEPPER` must be an independent secret-manager value with at least 32 characters. Credentials contain a random UUID and 256 random bits; only a domain-separated HMAC digest and six-character suffix are stored. The full credential is returned once and remains only in the console's current memory. It is cleared on principal change, account selection, another mutation or explicit dismissal. Rotation creates the replacement and revokes the old key in one transaction. Revocation, capabilities and the account deletion fence are rechecked immediately before provider dispatch under the same account/billing lock order. Auth deletion cascades credential rows while retaining financial accounts.

The verified owner can create up to ten empty accounts, each with a separate default developer project. Each account supports at most 100 non-revoked keys. Keys have explicit chat, streaming, image generation, embedding and optional private-file capabilities. Organization, project and key budgets are explicit positive spending ceilings, measured in minor currency units. They do not set provider prices or grant credit. All three scopes must be configured before paid admission. The console returns all bounded active keys, paginates every budget in deterministic account/scope order, and labels usage as the latest 100 calls. Changing the signed-in principal immediately replaces the entire stateful console. Every authenticated console request pins that principal so a token refresh cannot apply an old form to a new account.

Clients first obtain a quote for an operation and its input. The server signs a two-minute token binding key ID, provider, capability, translated exact request body, pricing version and maximum charge. Execution must carry the token in `X-Kova-Quote` and a stable `Idempotency-Key`. Changed input, another key, expiry, a new pricing version or a higher recomputed price fails before dispatch. Billing context carries the accepted fingerprint, pricing version and ceiling into the common provider transport for another check after asynchronous setup. Configured Azure deployment aliases are preserved when a request crosses both ingress and transport; the approved pricing contract and registry must identify that final billed deployment, with no guessed canonical-to-deployment pricing substitution. Provider responses retain only their content type; private upstream headers and raw error bodies are not forwarded.

Account exports use a service-only, owner-scoped projection of accounts, projects, key metadata, budgets, requests, purchases and credit ledger records. It never includes raw keys, credential digests, key suffixes, request fingerprints, internal rate data or arbitrary processor metadata. Auth deletion removes ownership, projects and credentials. Financial account IDs and immutable financial records remain for reconciliation; this source does not establish a legal retention duration or grant access after the owner is deleted. The operator must approve the minimal retention schedule and processor retention policy before paid activation.

The native Responses endpoint accepts bounded text/message history, strict function declarations and paired client-owned tool results, encrypted reasoning continuation, strict JSON Schema output, an explicit output-token ceiling and optional streaming; provider storage is always disabled. Schema/tool/history bytes enter the same signed quote and reviewed input bound. Function declarations do not authorize the server to execute tools. Image generation requires explicit size and quality under the approved meter. Embeddings accept at most 32 bounded text inputs. Client account/usage/price/URL fields, hosted tools, remote attachments and multimodal Responses content are rejected. Existing consumer plan accounting and model routing are unchanged.

The MCP adapter implements stateless Streamable HTTP, protocol negotiation, initialize/ping, scoped tool listing, quoting and non-streaming generation calls. It authenticates every request with the same key boundary. It supports scoped bearer credentials and the separately gated [browser OAuth consent and registration flow](developer-mcp-oauth.md). OAuth grants are bound to one developer project and do not grant access to consumer Projects or Library. No installable ChatGPT App or widget is claimed. Reference: [MCP Streamable HTTP transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Prepaid credit purchase and reversal source is described in [developer-prepaid-funding.md](developer-prepaid-funding.md). The first-party server JavaScript/TypeScript SDK lives in `sdk/javascript`; it enforces explicit client currency/budget, stable idempotency, bounded quotes and cancellation without implicit provider retries. Pricing administration is implemented separately. The bounded private text-file API and owner lifecycle are described in [developer-private-files.md](developer-private-files.md). Browser OAuth compatibility is a separate source package. Actual approved commercial rates, provider receipt contracts, payment/tax configuration, migration/deployment and live activation/canaries require the operator. Missing source is not classified as operator-only work.

Verification covers SQL ownership and privilege boundaries without service-role `SELECT auth.users`, atomic key rotation, secret deletion, scope changes/deletion fences between admission and dispatch, quote tampering/expiry/input/price changes, MCP scope/protocol handling, consumer/developer context isolation and the prior ledger conservation/fault suite. All provider calls in these tests are local fakes.

## Key-scoped usage retrieval

`GET /api/v1/usage?limit=25&offset=0` returns recent request records for the authenticated API key only, with sanitized token dimensions and customer charges in currency minor units. It uses the normal key authentication and rate limits and does not call a provider or create a charge. Limit is 1–100, offset is 0–10000; other parameters are rejected. The response contains `data`, `has_more`, and `next_offset`; the live list may change between reads. Organization-wide usage remains available only through the verified owner console. `GET /api/v1/usage?id=<request-uuid>` returns one sanitized usage record for the authenticating key, or the same 404 for missing and inaccessible requests. The `id` selector cannot be combined with pagination. This read-only operation does not call a provider or reserve credits.

## Model-specific reasoning effort

Responses accept an optional `reasoning: { "effort": "high" }` field. An approved pricing contract must explicitly list the supported values in `allowedReasoningEfforts`. The model catalog exposes these as `reasoning_efforts`, and the playground displays only the approved options for the selected model. Changing the effort invalidates the current quote. Reasoning remains within the approved output-token ceiling and is included in the signed request and metered settlement. No additional provider capability is enabled by default.

## Bounded inline vision

A Responses user message may contain one inline PNG image of up to 32 KiB and 512 × 512 pixels, with `detail: "low"`. Remote image URLs, provider file IDs, other media and multiple images are rejected. Enable only for a model/provider contract with a reviewed `maximumInlineImageTokens` upper bound and verified input-token pricing; the server reserves sufficient input tokens for both request bytes and the image bound. The Playground shows an image selector only when the approved model catalog advertises inline-image support. Larger images, other formats and full vision compatibility remain outside this initial implementation.

## Streaming in the Playground

Select Streaming responses to use the approved streaming-capability model list. The Playground requests a Responses quote with `stream: true`, sends the identical signed request after explicit confirmation, and renders only public output-text and refusal deltas. Failed, incomplete or truncated streams are distinguished from successful completion; cancellation never implies a refund or confirmed settlement. Consult Logs before retrying. The UI does not expose encrypted reasoning or internal event payloads.

## Advanced Playground options

Responses and streaming requests support additional JSON for instructions, strict structured outputs, client-owned function definitions, tool selection and project file IDs. The controls do not permit overriding the model, input, stream mode, token bound, reasoning effort or storage settings. All options participate in the same signed quote and server-side validation. Files exposes the project file ID for this purpose. The Playground does not execute client-defined functions itself.

## Bounded hosted web search (disabled until qualified)

The Responses endpoint accepts a single native web-search tool with low search context, an explicit `max_tool_calls` of 1–3 and nonstreaming execution. Use a chat-scoped key and an approved OpenAI model contract with the `responses_search` meter. For example, the additional request fields are:

```json
{
  "tools": [{ "type": "web_search", "search_context_size": "low" }],
  "max_tool_calls": 2,
  "stream": false
}
```

The server selects the required tool, rejects mixed hosted tools, and reserves the approved token and call dimensions before dispatch. A contract needs an approved `web_search_calls` price, a reviewed maximum search input bound, and evidence that search-content charges are included in the returned input-token meter. Fixed-block search pricing and unqualified Azure contracts are excluded. Only actual, uniquely identified completed search calls contribute to settlement; malformed or missing required tool evidence leaves the reservation for reconciliation. The user can supply these fields through Advanced request options. The API catalog advertises support only when a matching contract and runtime gate exist. `KOVA_DEVELOPER_WEB_SEARCH_ENABLED` remains off pending provider-specific metering verification. No upstream rates, provider calls, or payment activity were authorized by this implementation.

## Standalone moderation (disabled until qualified)

`POST /api/v1/moderations` accepts a public model alias and one nonempty text input of at most 8,000 characters. A separately scoped `moderation` key, reviewed `moderation_requests` pricing contract, signed quote and idempotency key are required. Only explicitly approved standard OpenAI moderation models are supported. The response must contain one matching classification result and a valid provider request ID before settlement. No token counts are invented; request counts appear separately in usage analytics and CSV exports.

OpenAI's standard moderation endpoint is free to use; Kova's own reviewed infrastructure and collection-cost policy determines any customer charge. This implementation does not establish a commercial rate. The staged workspace migration adds the new key scope, and `KOVA_DEVELOPER_MODERATION_ENABLED` plus the configured provider capability must be enabled only after migration replay, provider verification and owner review. Image moderation, bulk classification and specialized restricted classifiers are not part of this implementation.

Reference: https://developers.openai.com/api/reference/resources/moderations/methods/create

## Filtered model discovery and SDK parity

`GET /api/v1/models?id=<public-model>` returns the same catalog envelope as the list endpoint but contains only the matching alias's capability entries visible to the authenticating key. An unknown or out-of-scope alias returns the same 404. Invalid, duplicate and unknown query parameters are rejected. The JavaScript SDK now exposes this selector, the read-only usage list/detail operations, and quoted text moderation, with TypeScript declarations for reasoning and bounded hosted-search requests. These additions do not activate any provider or publish the private SDK package.

## Bounded source-image editing (disabled pending qualification)

`POST /api/v1/images` and the matching quote operation accept an optional `image` field containing one canonical inline PNG data URL, at most 32 KiB and 512 × 512. The prompt, output size, quality and count retain the existing generation bounds. With this field the server dispatches the existing multipart image-edit provider adapter; without it the generation contract is unchanged. Remote URLs, masks, provider-owned IDs and additional source images are rejected.

Image editing requires the image-generation scope, `KOVA_DEVELOPER_IMAGE_EDITS_ENABLED=true`, an enabled image adapter and an approved OpenAI image-token contract with a positive reviewed `maximumImageEditInputTokens` no greater than its reserved image-input token ceiling. The actual multipart bytes are reconstructed into the canonical quote fingerprint before reservation and dispatch; a changed image cannot reuse the signed quote. Image input token receipts are required for settlement. The model catalog and Playground expose the source control only for an eligible contract. The JavaScript SDK offers `images.edit`. No provider pricing, payment or live activation is implied.

## Explicit Web Search and Chat Completions endpoints

`POST /api/v1/search` accepts `model`, `query`, `max_output_tokens` and `max_tool_calls` (1–3). Quote the same input with operation `search`. The handler normalizes it to a nonstreaming native Responses request with one low-context required search tool; the existing reviewed search contract, scope, feature gate, authoritative search receipts and billing remain mandatory. The response is the native Responses envelope, including source annotations when supplied by the provider. This is grounded answer search, not an unrestricted crawler.

`POST /api/v1/chat/completions` accepts `model`, up to 100 text-only `messages` with system/developer/user/assistant roles, exactly one of `max_tokens` and `max_completion_tokens`, optional `reasoning_effort` and boolean `stream`. Quote operation `chat/completions` first. The handler uses the same native Responses meter and converts the verified provider output into a bounded Chat Completions JSON or SSE envelope, exposing the public model alias rather than the upstream deployment. Text, refusals, incomplete output and verified token usage are preserved; reasoning internals are not. A missing terminal event or invalid provider result never produces a successful completion. Native Responses remains the contract for structured outputs, function tools, files, multimodal inputs and hosted search. This is a documented subset, not drop-in compatibility with every OpenAI SDK option. The signed quote also binds the requested API operation; a quote issued for one API shape cannot be submitted to a different endpoint.

## Project-scoped lexical file search

`POST /api/v1/file-search` accepts `query` (up to 256 characters and 12 distinct terms), `file_ids` (one to four unique project-owned private file UUIDs), and optional `limit` (1–10, default 5). It requires an authenticated files-scoped key, `KOVA_DEVELOPER_FILE_SEARCH_ENABLED=true`, and a separate bounded read rate. It retrieves the selected files through the existing owner/project/key-locked RPC, verifies the content digest, length and expiry, then returns deterministic case-insensitive lexical matches from bounded overlapping Unicode windows. Result offsets are Unicode code points. Missing, foreign, corrupt or expired files fail the entire request. File content is data only.

The operation performs no provider call or inference reservation. Storage/read/CPU overhead must be covered by the reviewed platform operating allowance before activation. JavaScript `files.search` and Python `file_search` use this explicit endpoint. This is real lexical retrieval, not a hosted vector store, semantic embeddings search or automatic corpus indexing.

## Project-owned vector stores (staged database implementation)

The `/api/v1/vector-stores` resource supports list/retrieve, create, explicit entry upsert, entry list/retrieve/delete, cosine search, and store deletion. A key needs both files and embeddings scopes. Create POST body `{"operation":"create","name":"Docs","model":"<approved embedding alias>","dimensions":1536}` requires a stable Idempotency-Key. Upsert POST body uses operation `upsert`, store_id, entry_id, the same model, vector, text and optional project file_id; linked text must be an actual excerpt of that file. Search POST body uses operation `search`, store_id, model, vector and limit (1–20). GET id selects a store, id with entries=true and page lists entries, id with entry_id retrieves one entry, and DELETE id with optional entry_id removes a store or entry.

The caller obtains embeddings through the separately quoted Embeddings API or supplies its own compatible vectors. The store normalizes validated vectors and returns actual cosine scores, never a simulated match. There is no automatic file embedding or provider call in these operations. Each store is capped at 500 entries, 1536 dimensions, 30-day retention; owner-wide quotas cap stores, entries, dimensions and text. The SQL rechecks project ownership, current key scopes, account state and deletion fences under the existing owner lock. File deletion cascades linked entries. No anonymous or authenticated direct table access is granted.

The schema is staged in `supabase/pending/developer_vector_stores_v1.sql` and included in the migration materializer. It must pass isolated replay, retention and data-export integration (the owner-filtered export view is staged, but the account export pipeline has not yet been extended), pricing/operating-cost review, and production configuration before `KOVA_DEVELOPER_VECTOR_SCHEMA_READY` and `KOVA_DEVELOPER_VECTOR_STORES_ENABLED` are activated. The staged SQL and its integration tests are not yet verified. Automatic hosted indexing and retrieval tools remain separate work.

## Private conversation state (staged database implementation)

`/api/v1/conversations` supports creating, listing, retrieving and deleting project-owned text conversations. POST `{"operation":"create","id":"<caller UUID>","title":"Example"}` creates the resource; the same ID and title recover an existing resource. Append takes operation `append`, conversation id, expected_revision and item `{"id":"<stable item UUID>","role":"user","content":"Text"}`. Remove takes operation `remove`, conversation id, item_id and expected_revision. GET id retrieves a snapshot; GET id with item_id retrieves a single active item. DELETE id erases the conversation. List returns metadata, never message bodies. Duplicate identical appends recover the original item; concurrent mutations with an old revision return conflict. A removed item leaves only its identifier as a retry fence.

A chat- or streaming-scoped key is required. The server checks owner, project, key, account and deletion/lockdown fences inside the database transaction. Maximum 50 conversations per owner, 100 lifetime items per conversation, 8 KiB per message, 48 KiB serialized history, and 30-day retention. Conversation storage is independent of consumer chats and performs no implicit inference. Clients explicitly retrieve a snapshot, map active items to role/content messages and send them through the ordinary quoted Responses or Chat Completions flow; automatic server-side response appends, compaction and provider conversation IDs are not implemented.

The staged SQL, owner-filtered export integration and expiry worker must pass canonical migration replay before `KOVA_DEVELOPER_CONVERSATION_SCHEMA_READY` and `KOVA_DEVELOPER_CONVERSATIONS_ENABLED` are enabled. The separately gated vector export view is also connected to account export collection. No production schema or data is changed by committing this source.

## Native Decisions (gated)

POST /api/v1/decisions takes model, input (shared text, up to 16 KiB), and 1–16 uniquely named questions. Each question has type predicate, choice or score, name and instructions. Choices take 2–10 distinct string or boolean values; scores take 2–10 ordered labels. Optional option descriptions are bounded. Quote operation decisions with the exact input, then submit the matching signed quote and stable Idempotency-Key. This is a direct native OpenAI Decisions call for an operator-approved gpt-6-luna contract, not a Responses emulation.

The adapter sets explicit cache mode with no breakpoints. A valid authoritative receipt must show no cached or cache-write tokens, a matching provider model and a request ID from the transport or body. The dedicated decisions_tokens meter uses decision_input_tokens, never the ordinary Responses input rate for the same upstream model. There is no hard-coded commercial rate. The existing reservation, immutable rates and settlement path remain mandatory. Native refusals are preserved; invalid question identities, distributions and scores fail closed. Model names are mapped to the public alias.

Activation requires the reviewed workspace migration with the decisions scope, KOVA_DEVELOPER_WORKSPACE_V2, KOVA_DEVELOPER_DECISIONS_ENABLED, provider capability configuration, verified price registry, and live provider qualification. This first implementation supports only text, no prompt caching, images, JSON parts, streaming or voice linkage. JavaScript decisions.create and Python decisions use the same signed quote contract.

Reference: https://developers.openai.com/api/docs/guides/decisions

## Versioned agent definitions and metered single turns (staged)

`/api/v1/agents` manages project-owned text agent definitions. POST operation create with id (caller UUID) and definition containing name, public model alias, instructions and max_output_tokens (1–8192). POST operation update also requires expected_version. Updates append immutable versions; identical retries recover the original revision. GET lists current metadata, GET id selects the current definition, and GET id with version selects a historical revision. DELETE id erases all versions. The database rechecks owner, project, key, account and lockdown fences under an owner lock. Quotas are 20 definitions per owner, 20 versions per definition, and 200 total versions per owner.

`POST /api/v1/agent-turns` accepts agent_id, version, and input (bounded plain text). Request a signed quote with operation agent-turns, then execute with the same input, quote and stable Idempotency-Key. The server loads the exact version from the authenticated project. It fixes the model, instructions and output ceiling and binds the agent identity, version and creation time into the signed quote in addition to the canonical provider request fingerprint. Provider execution uses the existing independently approved Responses contract, and no model, instruction or tool override is accepted. The native Responses envelope is returned.

This is a versioned, single-turn text agent resource, not the native hosted Agents API, multi-agent orchestration, autonomous tool execution, or a persistent provider session. It performs no unquoted background work. JavaScript agents and Python agent_* methods implement the same explicit operations. Account export includes saved versions when the schema is ready. The staged migration, full authorization and billing tests, and reviewed operating allowance must pass before KOVA_DEVELOPER_AGENT_SCHEMA_READY and KOVA_DEVELOPER_AGENTS_ENABLED are activated.

## Developer Skills (staged text bundles)

GET, POST and DELETE /api/v1/skills manage private project-owned, versioned skill definitions with a chat-scoped key. POST create requires a caller UUID and definition containing name, description and instructions. POST update requires the same UUID, an expected_version and a new definition. GET id and optional version retrieve one immutable revision; GET without selectors lists metadata. DELETE id removes every revision. Definitions permit declarative text only, not executable scripts, tool permissions, credentials, external URLs or archives. Each owner has at most 20 skills and 200 total revisions, with up to 20 revisions per skill. Owner deletion cascades through stored versions; the export pipeline includes owner-filtered records when the schema is ready.

An agent-turn request may include skills as an ordered array of one to four distinct {id, version} references. The server fetches exact authorized versions, appends their instructions to the agent definition within the existing 8 KiB instructions ceiling, and binds the selected versions and creation identities to the signed quote. A changed, deleted or replaced version requires a new quote. No separate unmetered inference call is made. SDK skill CRUD uses the same scoped resource semantics. KOVA_DEVELOPER_SKILL_SCHEMA_READY and KOVA_DEVELOPER_SKILLS_ENABLED remain off until migration replay and isolation verification. Executable bundles, artifacts, and automated tool discovery remain outside this initial text-only implementation.

## Outgoing developer webhooks (staged)

The key-scoped /api/v1/webhooks resource supports list/retrieve, create, rotate, delete, queue a test event and inspect the most recent 50 deliveries. POST create accepts operation, caller UUID id, exact approved HTTPS url, and events (request.settled and/or request.rejected). POST rotate accepts id and expected_generation; POST test accepts id and stable event_id. GET id with deliveries=true lists delivery status. Create and rotate return signing_secret; other reads and exports exclude it. Registration is restricted to operator-approved exact URL destinations. No request body, model output, key secret, provider credential or cost/margin data is sent.

Terminal accounting events are independently discovered from committed request history; delivery cannot roll back a financial settlement. The existing authenticated internal maintenance worker claims at most three deliveries at a time, with durable leases, up to five attempts, exponential backoff, and bounded event retention. Delivery is at least once within the discovery/retention window, not exactly once or a guaranteed SLA. Receivers must deduplicate by event ID. Test deliveries are synthetic and do not incur inference charges. A revoked key, deleted account, banned account or lockdown blocks new delivery claims; already in-flight attempts may finish.

Each POST uses the exact JSON body and headers X-Kova-Webhook-Id, X-Kova-Webhook-Timestamp (Unix seconds), X-Kova-Webhook-Signature (v1=hex HMAC-SHA256). Sign the UTF-8 string event_id.timestamp.body with the returned signing secret; verify the signature in constant time, require a timestamp within 300 seconds and deduplicate event IDs. Rotate using the expected generation. Pending retries use the current signing secret; receivers should allow for a short in-flight rotation overlap.

Activation requires canonical migration replay, verified database/worker tests, reviewed endpoint ownership and network policy, KOVA_DEVELOPER_WEBHOOK_SCHEMA_READY=true, KOVA_DEVELOPER_WEBHOOKS_ENABLED=true, a securely generated server-only 32-byte hex DEVELOPER_WEBHOOK_MASTER_KEY and comma-separated KOVA_DEVELOPER_WEBHOOK_DESTINATIONS (exact canonical HTTPS URLs). The server resolves A records, refuses nonpublic or mixed answers, pins the selected address while validating the original TLS hostname, forbids redirects, and limits outbound requests. IPv6-only endpoints, arbitrary URLs, custom headers, automatic customer registration and real delivery activation are not provided by this staged implementation.

## Developer Batches (staged asynchronous execution)

POST /api/v1/batches with operation create, stable batch UUID id, currency, maximum_charge and 1–8 items. Each item requires a distinct UUID, a bounded nonstreaming Chat Completions request (text only, up to 16 messages and 2048 output tokens), and its fresh quote_token from operation chat/completions. The server verifies every signed quote, current contract and scope, compares the sum of conservative maximum charges to the explicit batch budget, and stores separate signed authorizations bound to that key, project, batch, item and immutable pricing version. The caller bearer secret is never stored. No inference runs during submission.

GET lists metadata or retrieves a batch with id; GET id and item_id returns an individual input, result and accounting status. POST operation cancel with id prevents new claims; already running items may finish. The authenticated internal worker claims one item per invocation, rechecks owner/key/lockdown and signed authorization, and dispatches through the ordinary metered path with a deterministic idempotency key. A crash or ambiguous result is marked uncertain and is never automatically retried. A result is completed only if the ledger confirms settlement. Requests reserve available credit individually at dispatch, not at submission; later budget exhaustion, revocation, price changes or emergency controls can prevent execution. No discounted upstream batch rate or completion SLA is claimed.

Authorizations expire after 24 hours; queued items are canceled on expiry and records are purged seven days later. Each owner may retain at most ten batches. The output and export records exclude internal authorization and lease tokens. Enable only after canonical migration replay, billing and worker qualification, with KOVA_DEVELOPER_BATCH_SCHEMA_READY=true and KOVA_DEVELOPER_BATCHES_ENABLED=true. SDK batch methods manage these resources. This is a Kova durable queue, not a proxy for the upstream Batch API.

## Scheduled developer automations (staged)

The separate /api/v1/automations resource uses the durable metered batch queue. Each automation is an explicitly authorized finite schedule of one to eight nonstreaming text invocations, each with its own quote_token, UUID and strictly increasing run_at (canonical UTC ISO timestamp with milliseconds). Dates must be between one minute and 23 hours from submission. The aggregate maximum_charge, expiry, deterministic billing identities, and owner/key/project fences are inherited from Batch. Signed deferred authorization also binds each invocation's due time; the worker rejects early or altered execution.

GET lists automations, retrieves one by id, or retrieves an invocation by id and item_id. POST pause, resume and cancel require the automation id. Pause prevents additional claims; resume can execute an overdue unclaimed item while its authorization is valid; cancellation prevents new claims. In-flight work is not interrupted. A disabled automation feature prevents claims even if ordinary batches are enabled. JavaScript automations and Python automation_* methods expose the resource. Enable KOVA_DEVELOPER_AUTOMATIONS_ENABLED only alongside verified batch schema, billing and worker activation. Indefinite recurrence, external actions, and full agent-session scheduling remain outside this initial finite, text-only implementation.

## Isolated developer analysis (staged)

POST /api/v1/analysis accepts model, bounded text input and max_output_tokens (1–2048). Requires a signed quote and file_analysis scope. Server constructs one automatic 1 GB network-disabled container, with no prior context or provider identifiers and at most one built-in tool call. The result is bounded text under the public model alias; the server deletes the observed container before returning. Missing or ambiguous receipts remain uncertain. The responses_analysis contract requires approved token and container_1g_sessions rates, plus a reviewed maximumAnalysisInputTokens overhead bound. The provider and wallet gates remain disabled pending qualification. SDKs include analysis. This does not provide persistent container CRUD or hosted shell.

### Multiple agent invocations in batches and schedules

Each batch or scheduled invocation may specify operation "agent-turns" instead of the default "chat/completions". Supply the versioned agent-turn input (agent_id, version, input, optional versioned skills) and a fresh quote for that exact operation. The durable authorization binds the operation and agent/skill creation identities, and the worker checks them again before dispatch. Multiple distinct agent definitions can run under one aggregate budget, with individual outputs and accounting records. Agent invocations must have a nonstreaming output ceiling of at most 2048 tokens. This is independent agent execution, not model-directed delegation or automatic chaining of outputs.

## Client-executed Computer Use proposals (staged)

POST /api/v1/computer-use accepts model, input, an inline PNG screenshot, and max_output_tokens. Requires computer_use scope and an exact signed quote. The native Responses computer tool returns at most one proposed click, scroll, wait, or screenshot action. Kova never executes actions, acknowledges safety checks, or retains provider context. Pending or missing safety checks, unsupported actions, and out-of-bounds coordinates produce a blocked result. The caller owns the isolated UI and must verify and approve any action. The separate responses_computer meter requires approved model token rates, screenshot and tool-overhead bounds, and explicit provider and workspace activation. JavaScript computerUse.propose and Python computer_use use the signed quote and wallet. This is not a hosted browser or persistent desktop session.

## Developer Cloud Browser snapshots (staged)

POST /api/v1/browser reads one approved public HTTPS page in a new isolated Browserbase session. The caller supplies a public model alias and canonical URL, with no query, fragment, authentication, cookies or custom headers. Requires a cloud_browser-scoped key, explicit owner spending authorization via the ordinary signed quote, an approved browserbase-readonly-60s model contract with one browser_sessions_60s unit, an operator origin allowlist, and KOVA_DEVELOPER_BROWSER_ENABLED. Browserbase is reserved through the same wallet ledger as model requests. The published rate must cover the entire allocated 60-second session including provider billing rounding; it is not a claim of measured per-second usage. The provider session is hard-limited to 60 seconds; Kova has a shorter local deadline, twelve read-only subresource requests, an eight MiB transfer ceiling, disabled scripts and WebSockets, DNS-pinned egress, no write actions, and account/key/site-rule checks on egress. A completed session produces bounded text, title and a JPEG snapshot; provider session identifiers stay private. Uncertain execution remains reserved for reconciliation. SDKs expose browser.snapshot and browser_snapshot. No authenticated browsing, arbitrary navigation, persistent desktop or autonomous actions are provided by this operation. Do not enable until provider, isolated browser and ledger tests pass.
