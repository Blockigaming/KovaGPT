# Auth migration rehearsal source specification

This document defines the one-purpose, disposable Auth migration rehearsal receiver. Despite the historical filename, the receiver is not operated through Lovable. It accepts only `POST /api/internal/auth-migration/rehearsal`.

## Safety boundary and configuration

The receiver is disabled unless all server-only settings are valid:

- `AUTH_MIGRATION_REHEARSAL_ENABLED=true`;
- `AUTH_MIGRATION_SOURCE_ID` is a nonempty logical identifier for the source and is neither a Supabase destination reference nor a secret;
- `AUTH_MIGRATION_DESTINATION_PROJECT_REF=oztdrjtdglkizlewnulh`;
- `AUTH_MIGRATION_REHEARSAL_DATABASE_URL` passes the destination-affinity checks below;
- `AUTH_MIGRATION_BRIDGE_SECRET` contains at least 32 characters.

`mfbycmbjygcfkrsuepxf` identifies the real NEW project. It is prohibited as the source ID, destination, database hostname, database username, or any trusted project-affinity value. The request cannot specify or override a database URL.

The database URL must use `postgres:` or `postgresql:`, database `postgres`, and port `5432`. It must be either:

1. direct: host `db.oztdrjtdglkizlewnulh.supabase.co`, user `postgres`; or
2. Supavisor session pooler: a host ending in `.pooler.supabase.com`, user `postgres.oztdrjtdglkizlewnulh`.

Port `6543` and all other transaction-pooler configurations are prohibited. The deployment must run exactly one receiver replica.

The source exporter MUST use read-only source credentials and MUST NOT alter the source. It may export only persistent user and identity fields in the schema below. Sessions, refresh tokens, one-time tokens, `flow_state`, MFA challenges, MFA AMR state, pending recovery state, pending email/phone changes, `auth.instances`, and `auth.schema_migrations` are prohibited.

## Exact JSON payload

The UTF-8 request body is a JSON object with exactly these fields; unknown or missing fields are rejected:

```json
{
  "source_id": "operator-configured-logical-source-id",
  "destination_project_ref": "oztdrjtdglkizlewnulh",
  "users": [],
  "identities": []
}
```

Each user contains exactly:

- `aud`
- `banned_until`
- `confirmation_sent_at`
- `confirmed_at`
- `created_at`
- `email`
- `email_confirmed_at`
- `encrypted_password`
- `id`
- `invited_at`
- `is_anonymous`
- `is_sso_user`
- `last_sign_in_at`
- `phone`
- `phone_confirmed_at`
- `raw_app_meta_data`
- `raw_user_meta_data`
- `role`
- `updated_at`

Each identity contains exactly:

- `created_at`
- `id`
- `identity_data`
- `last_sign_in_at`
- `provider` (`email` or `google` only)
- `provider_id`
- `updated_at`
- `user_id`

Every listed field is present; JSON `null` represents a database null. The receiver does not rewrite email bytes. A temporary case-folded value is used only to reject duplicate user emails. A `(provider, provider_id)` pair may occur only once and every identity must reference a supplied user. The request is limited to 256 KiB, 100 users, and 200 identities.

`instance_id`, identity `email`, pending email/phone change fields, and recovery fields are not accepted. Identity email is generated by the destination Auth schema and is never inserted directly.

## Exact raw-body HMAC protocol

The sender transmits the exact bytes it signs. There is no JSON recanonicalization. Required headers are:

- `Content-Type: application/json` (exact media type);
- `X-Auth-Migration-Timestamp`: ten-digit Unix time in seconds;
- `X-Auth-Migration-Nonce`: 32–128 base64url characters generated from at least 192 cryptographically random bits;
- `X-Auth-Migration-Signature`: 64 hexadecimal characters.

The signature is lowercase hexadecimal HMAC-SHA-256 using `AUTH_MIGRATION_BRIDGE_SECRET` over these exact UTF-8 bytes:

```text
v1\n<TIMESTAMP>\n<NONCE>\n<EXACT_RAW_REQUEST_BODY>
```

The receiver retains a bounded raw body, checks a ±300-second timestamp window, and compares decoded 32-byte MAC values in constant time. It never logs bodies, signatures, nonces, secrets, URLs, emails, password verifiers, or identity data.

## Replay, retry, and completion rules

A bounded process-local nonce cache retains valid authenticated nonces for the replay window. Reuse is rejected. A process-local completion flag makes the receiver return Gone after one successful import. A process restart is still protected by the destination-empty assertion. No request-time DDL is permitted.

The nonce cache is intentionally suitable only for the required single-replica disposable receiver. Operators MUST NOT scale it beyond one replica. Failed authenticated requests consume their nonce; a retry uses a new timestamp, random nonce, and signature. There is no overwrite or general idempotency behavior.

## Read-only schema preflight and transaction

Before inserting, the receiver reads column and constraint metadata for `auth.users` and `auth.identities`, including data type/UDT, nullability, default, identity status/generation, generated status/expression, primary keys, unique constraints, and the identity-to-user foreign key. It compares insert fields to an explicit reviewed persistent-field/type allowlist. Generated or identity columns are never inserted. `confirmed_at` is inserted only when the live preflight reports it writable; a generated `confirmed_at` is omitted. Any unreviewed type, generated/identity status, or required-constraint mismatch fails closed.

**Modern Supabase metadata note:** authoritative FK validation must not rely solely on `information_schema.constraint_column_usage` returning referenced-table fields. In the disposable rehearsal project, that view returned blank referenced-table fields for the valid `identities_user_id_fkey`, while `pg_constraint` authoritatively reported `FOREIGN KEY (user_id) REFERENCES auth.users(id) ON DELETE CASCADE`. Any future preflight patch must preserve the exact FK requirement while using authoritative PostgreSQL catalog metadata when information-schema visibility is incomplete; it must never simply skip the FK check.

One database transaction performs:

1. `BEGIN`;
2. local 5-second lock timeout, 30-second statement timeout, and 30-second idle-in-transaction timeout;
3. a PostgreSQL advisory transaction lock;
4. schema preflight;
5. assertions that `auth.users` and `auth.identities` each contain zero rows;
6. user inserts followed by identity inserts with preserved UUIDs;
7. actual destination queries checking counts, provider distribution, duplicate provider subjects, orphan identities, and fingerprints;
8. comparison of destination evidence to the signed request evidence;
9. `COMMIT` only if every check passes.

Every failure attempts `ROLLBACK`. The HTTP request never creates, alters, or drops schema objects.

## Safe diagnostic behavior

Authenticated requests may expose only a small stable `RehearsalError` code. Raw PostgreSQL/TLS exceptions, exception messages, stack traces, database URLs, credentials, HMAC values, request bodies, emails, password verifiers, identity data, and metadata remain prohibited from responses and logs.

A raw `pg` connection failure is mapped to `database_connect_failed` with HTTP 503 on the diagnostic branch. This diagnostic exists to distinguish container-side `pg`/TLS connection failures from schema/transaction failures without weakening certificate verification or database-affinity guards.

## Response and evidence formulas

A success response contains exactly:

- `users`
- `identities`
- `user_uuid_fingerprint`
- `identity_fingerprint`
- `provider_distribution`
- `status`

The evidence is computed from rows queried from the destination inside the transaction:

- user UUID fingerprint: MD5 of sorted `auth.users.id` strings joined with `"\n"`;
- identity fingerprint: MD5 of sorted `user_id + "|" + provider + "|" + provider_id` strings joined with `"\n"`.

Identity `id` is deliberately excluded from the identity fingerprint formula. Responses never contain emails, password verifiers, identity data, secrets, nonces, signatures, or database URLs.

For a controlled eventual real rehearsal, external acceptance evidence is 5 users, 6 identities, providers `{ "email": 3, "google": 3 }`, user fingerprint `41c2d9f45588bcaa85ef8ec06f81d993`, and identity fingerprint `f9ec822e4b641dbfe73789c76b911ab1`. These values are not hardcoded as receiver success output. Repository tests use synthetic records only.
