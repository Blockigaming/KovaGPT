# Durable same-chat summaries

The source implementation is deployment-gated and has not been activated in production. Existing recent-turn chat and cross-chat memory remain available while the gate is off.

Admission uses the existing authenticated, paid, consent-checked `/api/memory` POST. The browser creates its optional summary snapshot inside `enqueueMemoryWrite` and pins the request to the scheduling account's token. A durable owner epoch is captured before request-body or provider work. Clearing memory advances that epoch and deletes both summary stores atomically, so requests already admitted on other devices cannot recreate either store afterward. Chat-specific deletion also advances the owner epoch, conservatively discarding concurrent writes in other chats. Genuinely new requests from another consent-enabled browser retain the existing browser-local consent behavior. Temporary conversations never produce snapshots. A converted Temporary conversation includes only turns after its saved `memoryStartIndex`; neither its title nor its earlier private turns enter the request.

`chat_context_summaries` holds one row per owner and chat. Only the service role may mutate it or call its queue/claim/settle functions. Authenticated owners can read their own rows under RLS. The RPCs use invoker privileges and fixed empty search paths. Account export includes these rows. Beginning account deletion clears both memory stores and advances the epoch, permanently retiring old summary leases even if the outer deletion subsequently fails and releases its fence. Final Auth deletion cascades remaining owner metadata.

Chat transport contains at most the latest 100 messages, while the browser archive stays intact. The model ordinarily receives the latest 12 messages. The browser reads an owner-scoped summary descriptor and computes SHA-256 over its complete original eligible prefix, including text omitted from excerpts. The chat request carries that bounded digest proof; the server requires it to match the current owner/chat summary row, covered prefix, and privacy boundary. This is consistency checking of user-supplied history, not independent attestation of its truth. Edits, truncation, or changed boundaries reject incompatible summaries. When the worker lags behind, at most 12 intervening message excerpts (2,000 UTF-16 code units each) bridge the summary to the recent history; summaries with a larger gap are rejected. A summary can omit detail and is explicitly presented to the model as fallible data; recent turns take precedence. It is separate from cross-chat memory selection.

Long conversations advance incrementally. Each worker input contains the exact previous completed summary plus at most 88 new message excerpts, limited to 256 UTF-16 code units each. The database accepts a nonzero base only when its row ID, cumulative count, digest, and privacy boundary still match the completed record. An edit restarts from a fresh prefix. Cumulative metadata is bounded to one million messages; transport and per-job input never grow with that archive length. While the consented conversation remains open, the browser checks for progress every 15 seconds and queues the next bounded increment through the privacy write coordinator. Catch-up POSTs skip the separate cross-chat summarizer. The loop stops when caught up, when an unchanged snapshot has exhausted its retry budget, when consent/account state blocks writes, or when the conversation closes; network failures back off to 60 seconds. Reopening or updating the conversation resumes eligible work.

Queue admission is capped at 8 pending/processing rows and 250 total rows per owner. New snapshots replace pending input and advance a revision. Worker claims have independent UUID leases lasting three minutes, run at most two jobs per batch, and use the existing `UTILITY` provider role with a 45-second timeout. Success or bounded failure must settle against the exact row, revision, and lease. Superseded workers and workers whose rows were deleted cannot publish. Failures use exponential backoff and stop after three attempts.

Raw excerpts are cleared on completion or final failure. They become ineligible after 24 hours; each authenticated worker call clears up to 500 expired inputs, including abandoned final-attempt leases. Cleanup continues when the generation flag is disabled: the endpoint then performs retention cleanup and claims no provider work. Keep the dedicated worker secret and schedule active for retention, and monitor whether repeated cleanup calls are needed to drain a larger backlog. Completed summaries remain until saved-memory/account deletion or a later compatible replacement.

To activate, the deployment owner must apply the matching migration and application revision, verify owner isolation and memory/account deletion in an isolated environment, choose a provider budget, set `KOVA_CHAT_SUMMARIES_ENABLED=true` and a dedicated `CHAT_SUMMARY_WORKER_SECRET`, and schedule authenticated POSTs without a body or query to `/api/internal/chat-summaries`. The endpoint does not inherit `CRON_SECRET` and refuses unauthenticated calls; provider work additionally requires the enabled flag. No activation, scheduler, secret, migration, or provider-credit change was performed by this source work.

A successful batch returns `purged`, `claimed`, `completed`, `retrying`, `failed`, and `superseded` counts without transcripts or summaries. Monitor nonterminal backlog age, terminal failures, and raw-input expiry; revoke the flag to stop further admission and provider work. Memory deletion remains available when the feature is disabled. Retry after fixing the underlying provider/database problem by submitting a new history snapshot; an unchanged terminally failed snapshot is not silently restarted forever.
