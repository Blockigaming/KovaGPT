# Installed web app, share intake and Web Push

This is repository source and offline/mock test evidence. No browser subscription, provider delivery, production migration or worker activation was performed. This package does not create native iOS, Android, macOS or Windows applications.

## Implemented behavior

- The manifest and `/kova-sw.js` enable browser installation and a public offline fallback. A supported `beforeinstallprompt` gets an explicit Install button; other browsers use their own Install app/Add to Home Screen command. Only `/offline.html` is cached. Private navigation, API, chat and document responses are never copied into a service-worker cache.
- POST `share_target` accepts text/title/HTTP(S) URL only, at most 64 KB raw and 12,000 text characters. Files, duplicate fields, unknown fields and unsafe URLs fail closed. At most five local tickets exist. A ticket expires after five minutes; expired bytes are removed on the next worker activity, so closed browsers are not claimed to execute a background erasure timer. No input is uploaded or sent to a model. An authenticated owner previews the ticket and explicitly chooses Use in chat, which hands a draft to the existing composer. Repeated preview is safe under React Strict Mode. Consume, discard, account change and device reset erase the local body.
- Installed-app state uses `kova-pwa-v1` IndexedDB. Owner updates first verify the actual current browser session and compare a durable service-worker epoch. Every owner-bound message carries that epoch, with a final synchronous principal guard before posting. A stale tab cannot restore an old account or binding after another tab changes owner. The same user can open another tab without invalidating the current epoch.
- Settings → Notifications offers explicit browser notification permission, subscription, per-device revoke, and persisted quiet hours. Existing notification category/in-app preferences are rechecked immediately before delivery. Current verified Auth, ban, deletion fence and Lockdown state are required. Revoke stays possible while delivery is disabled or fenced.
- Only immutable event/source IDs, timestamp and subscription ID cross the push transport. The displayed text is a generic update notice; task bodies, sender names and billing content never appear on the lock screen. A per-binding receipt is persisted before display, retaining all unexpired IDs (maximum 2,048, fail closed at capacity) for the 24-hour source window. Lost server settlement cannot repeat the same notification after dismissal. This favors at-most-once display: a browser crash between receipt and display can suppress that update, which remains available in the in-app inbox.
- SQL claims one unread post-consent event per device with deterministic timestamp/source/UUID ordering. Leases/revisions are checked before send and settlement. Quiet hours retain the cursor; suppressed/read events advance it. Each worker request processes at most three devices. Expired endpoints erase encrypted credentials; revoked rows are pruned after seven days in batches of 100.
- Subscriptions are encrypted with a context-separated key derived from the existing connector encryption key and authenticated to the owner and immutable device UUID. They are service-only. The browser retains only its native subscription and a revocation-only capability. Clearing a binding first removes local consent, then queues a bounded revocation retry and attempts native unsubscribe. Late pushes cannot display without the matching local binding. Pending revocations retry on subsequent app owner initialization or worker activation.
- `resetPrincipalDeviceData` awaits the service-worker erasure acknowledgement and reports `pwa_clear_failed` if it cannot prove removal. Settings includes that failure in its result. Unresolved identities cannot initiate cleanup.

## Activation that remains with the owner

The runtime is disabled by default. The owner must review/apply the repository migration and deploy the source, then provide `WEB_PUSH_ENABLED=true`, a matching P-256 `WEB_PUSH_VAPID_PUBLIC_KEY`/`WEB_PUSH_VAPID_PRIVATE_KEY` (base64url), a contact `WEB_PUSH_VAPID_SUBJECT` (`mailto:` or HTTPS), the existing `CONNECTOR_ENCRYPTION_KEY`, and a dedicated `WEB_PUSH_WORKER_SECRET` through the approved secret-entry mechanism. No secret values are in this repository.

An authorized private scheduler calls `POST /api/internal/web-push` using only its dedicated Bearer secret, no query or body, approximately once per minute. The worker validates configuration and records a two-minute heartbeat; the browser exposes subscription controls only when that heartbeat matches the current configuration. Manual provider/browser smoke must include opt-in, a generic real notification, quiet hours, revocation, account switching and signout. Browser vendors/OS installation requirements vary. Fixed supported push services are FCM, Mozilla Autopush and Apple Web Push; unsupported endpoints are explicitly rejected rather than allowing arbitrary outbound URLs.

No live Azure settings, identity, network, DNS, secrets or billing changes are part of this package. Public install/share functionality does not enable push delivery.

## Account portability and deletion

Export `web_push_preferences` by `user_id` (deterministic key `user_id`) and the service-only `web_push_subscription_export_rows` view by `user_id` (key `id`). The latter projects `user_id,id,revision,active,consented_at,created_at,revoked_at`. Never export endpoint hashes, encrypted subscription bytes, device capabilities, worker leases or delivery cursors. All subscription/preferences rows cascade on Auth deletion; the account fence prevents new consent or delivery during deletion. Local reset/signout removes that device's matching binding and share bodies.

## Verification and references

Executable tests cover the complete [RFC 8291 encryption vector](https://datatracker.ietf.org/doc/html/rfc8291#section-5), [VAPID](https://datatracker.ietf.org/doc/html/rfc8292), actual service-role SQL consent/access/lease/cursor/quiet-hour operations, actual compiled browser/API principal races, and the real service worker in Chromium. Push lifecycle tests use a native DevTools push event with a display adapter; no live push provider or desktop notification is invoked. Share support follows the [manifest share_target contract](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target).
