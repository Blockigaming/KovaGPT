# Prepaid developer funding

Source includes approved fixed-credit offers, hosted Stripe Checkout, a verified webhook inbox, leased reconciliation, immutable wallet entries, refund/dispute liability handling and a principal-scoped console. `KOVA_DEVELOPER_PAYMENTS_ENABLED` defaults to false. No offers, credit, API calls, payments or deployments are created by applying the source migration alone.

The operator must configure `DEVELOPER_PAYMENTS_ENV` as `sandbox` or `live`, the matching existing Stripe API credential, a pinned HTTPS `DEVELOPER_PAYMENTS_ORIGIN`, an independent `DEVELOPER_PAYMENTS_WEBHOOK_SECRET`, and `DEVELOPER_FUNDING_WORKER_SECRET`. A private scheduler POSTs an empty request to `/api/internal/developer-funding` with that bearer secret. The worker remains available while new purchases are disabled. It drains at most five attempts per call, serializes processor reads with a two-minute lease, retries transient failures after five minutes, and settles available credit against recorded funding debt without taking any active request reservation. Paid receipts become eligible every fifteen minutes even without a webhook. Deterministic oldest-check ordering prevents new checkouts from permanently displacing them; failed proof records a reconciliation state and safe diagnostic code for retry.

An offer fixes the environment, one-time Stripe Price, currency, exact subtotal, credit amount, refund/dispute reserves, maximum aggregate processor fee, reviewed tax policy, approval evidence and expiry. Credit cannot exceed the pre-tax subtotal. These are owner-approved commercial inputs; no rate, fee split, tax exemption or active registration is guessed. This first implementation requires processor settlement in the offer currency without FX. Automatic tax requires a compatible exclusive-tax Price and completed tax calculation. An explicit reviewed exemption records its owner's tax-review reference. The administrative approval path must verify the current Stripe Price and settlement-currency compatibility before activating an offer.

Checkout creation has a durable owner/account-scoped idempotency key. Current offer, price, settlement currency and tax readiness are checked immediately before the first dispatch. Its exact parameters and start time are then recorded under the owner and lease fence. An uncertain retry reuses that admitted payload and Stripe key even if readiness later changes. The create is never repeated after 23 hours. Instead, each worker claim scans at most 100 authenticated Checkout sessions in the closed creation-time interval and persists its cursor and candidate. Exhaustive discovery recovers one matching session or proves no session exists, releasing the unpaid attempt. Two distinct matching sessions remain a concrete processor ambiguity for operator investigation. A later verified webhook can also recover the session ID. Closing the browser or visiting the success URL never grants credit.

The webhook verifies Stripe's timestamped signature and environment before admitting an event. It retrieves the referenced processor resource to discover the attempt, records the event once, and acknowledges the durable queue. The worker independently retrieves the complete Session, PaymentIntent, captured Charge, settlement BalanceTransaction and bounded refund/dispute records. It validates price, quantity, account/attempt metadata, currency, tax, amounts and actual aggregate fees. No client-supplied monetary field or raw webhook object is settlement evidence. Missing fees or incomplete refunds remain pending. More than 1,000 refund records on one charge exceeds this bounded adapter and requires processor review.

First settlement records the purchase and grants credit atomically. Replay never grants credit twice. Refunds and active/lost disputes remove only available credit and record any shortfall as debt, suspending further spending. Active provider reservations remain untouched. A verified won dispute releases its liability; irreversible refunded principal cannot move backward. New money and later reservation releases can repay debt. Actual aggregate processor fees above the approved ceiling retire the offer and suspend the affected account for pricing review. The original processor fee is recorded as a verified total; percentage/fixed splits remain null rather than fabricated. A conservative server-recorded collection rate includes approved fee/reserve ceilings and observed higher fees. Both quote ingress and common provider metering apply at least that floor while preserving the accepted maximum charge.

Pending or unknown payments reject the account-deletion fence before Storage cleanup. Settled or expired attempts do not block deletion. Deletion removes personal ownership and credentials; minimal financial records remain for reconciliation under an operator-approved retention schedule. Owner exports include safe payment attempts, credit reversals and debt, without checkout URLs, API keys, processor metadata, fee evidence or credential hashes. The console continues to show prior payment status when purchases are disabled.

Offline verification uses real PostgreSQL semantics in PGlite, real Stripe HMAC verification, fake processor transport and the actual server driver. No test makes a provider or Stripe network request. Live tax/payment configuration, an approved commercial offer, scheduler/deployment and a real sandbox receipt canary are operator work.
