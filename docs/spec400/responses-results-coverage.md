# Responses and results coverage

This record describes the response/results implementation in the spec400 application. It is not a claim that production services or every screen have been tested.

## Implemented

- 191–193, 197–210: editorial Kova label, restrained aligned user messages, reading-width/size preferences, safe Markdown and semantic tables. Complete explicitly delimited writing (quotation or writing/email/message/prompt/letter/document/draft fence) and prose sections over 800 characters use one reusable content-box component. Every parsed code block uses a code box. Boxes use 12px corners, 16px padding, 44px headers, desktop header Copy, and mobile full-width footer Copy text/Copy code. Copy uses the box source only, confirms for two seconds, and exposes selection after failure. Explicit code filenames are sanitized and downloadable.
- 211–214: completed-response Copy response, Save to Library, feedback and More; Retry, Continue from here and private Copy link. Selection keeps native browser behavior and offers Ask, Rewrite, Shorten and Copy below the response rather than covering the selection. Rewrite and Shorten require explicit review/generation, use the existing selection endpoint and preserve untouched content.
- 215–226: the existing editor supports an embedded Result pane through ResultDescriptor/onOpenResult, with title and Edit, Versions, Export, Share, More controls. Real manual editing, undo/redo, existing canonical collaboration persistence, conflict recovery, version previews before restoration, heading outline and title-based export names remain. Proposed passage changes have a diff and individual-change acceptance. History preserves revisions; guest restore creates a new local revision. Share previews an immutable text snapshot before invoking the browser share surface or copying that snapshot.
- 227–231: explicit Run preview gates sandboxed static website preview; generated raster images retain aspect ratio and expose Save to Library through the existing image-save operation, Download, and View full size. Generating state stays in the response without fake percentages.
- 233–241: citations matching actual source records open a 420px Sources inspector, fullscreen on phones. Known publication metadata and supporting snippets are shown; absent retrieval time is explicitly unavailable. Actual operation events are grouped in Activity. Long waits display elapsed time without a remaining-time prediction.
- 257–259, 396: only a valid persisted-result create receipt in a done scheduled_task activity can produce the gray Scheduled task created link with a green 16px checkmark. It links to the existing /scheduled-tasks?taskId=<UUID> detail contract. Only a confirmed-result not-created receipt says Scheduled task not created with its actual reason. A transport/readback failure remains Scheduled task status unconfirmed and requires checking before retry. Running, canceled, unconfirmed, malformed, prose-only and synthetic-review states cannot produce success.

## Genuine remaining gaps

- This baseline has no production chat scheduled-task creation producer. The receipt contract and renderer are integrated, but no UI invents a persisted receipt from an assistant claim or generic activity success. Real chat-to-scheduler acceptance remains blocked on that producer.
- Library save/read contracts do not contain a source conversation/message reference. Saved objects are real, but item 232/287 source backlinks cannot be honestly populated by a visual-only change.
- Existing Sources records carry web URL/title/domain/snippet and optional publication date. The backend does not provide retrieval time or other source kinds; the inspector does not invent them.
- Existing durable result versions do not expose operation-origin provenance. Newly accepted revisions are identified as User edit or AI revision in the current session; old/reloaded revisions stay neutral rather than inventing origin.
- Public share-link creation/revocation is not implemented for results. The supported Share control shares a reviewed frozen text snapshot through the device share mechanism; it does not claim to create a managed public link.
- Live provider rewriting, persisted collaboration, Library saving, image persistence/download from real provider URLs, and office export rendering still need connected integration/browser verification. No paid/provider operation or deployment was performed.
