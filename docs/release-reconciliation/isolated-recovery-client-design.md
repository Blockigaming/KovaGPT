# Local design: isolated managed Auth restore

Status: unexecuted design, 2026-10-30. This does not authorize a restore, qualify an image or target, or change the frozen data-free probe. No customer data, credential values or private source catalog facts are included here.

## Required sequence

1. Merge the reviewed recovery/catalog/client-tool source and capture a fresh database envelope with that exact catalog implementation. A previous envelope with extension rows lacking owner or the old `NOT LIKE 'pg_%'` namespace predicate cannot silently become a new complete source catalog. Pin capture workflow run ID, source SHA, artifact ID, ciphertext byte size and SHA-256 from its success receipt. The receipt must prove actual encryption/decryption round-trip and complete required table coverage.
2. Obtain a successful actual native data-free probe on the pinned PostgreSQL17.6.1.155 image. Independently review the observed four exact baseline fingerprints, exact source metadata coverage, effective firewall evidence and limitations. Its two targets are destroyed; their cluster identifiers are never reused as future target pins.
3. Build and qualify the final operator-client image without source credentials, ciphertext or passphrase. Freeze its actual OCI content ID, complete tool/runtime version/hash inventory and source/build recipe. The current PG-only client has no proved Python/Node/GPG runtime and cannot execute the real restore engine.
4. In one fresh public GitHub-hosted Ubuntu24 runner job, prepare owned private files and download only the pinned ciphertext artifact to the host. Authenticate the GitHub artifact by run/repository/source/artifact identity and the reviewed byte/hash pins; perform no decryption. Collect any needed current source metadata in a separate short-lived process/container and destroy it; remove its production URL environment before any target/client setup. Do not give the source URL, API credentials, hosted Auth credentials or provider runtime keys to the client, target, Docker build or restore step.
5. Prepare two new template0-plus-extension targets using the reviewed bootstrap recipe and the same complete source role/schema/extension metadata. Compare all four unnormalized baseline fingerprints against each other and against the independently reviewed data-free baseline. Require exact native role/schema/extension-owner compatibility. Extension member source semantics are an additional distinct qualification; owner equality alone cannot prove them. If the full restored schema comparison later differs, recovery remains unqualified rather than waiving the difference.
6. Lock the final client and both servers before they process any plaintext: private internal dual-stack bridge, no host ports/socket mounts/tunnels, nonroot client, read-only root filesystems, no added capabilities, no-new-privileges, disabled image health checks. Install exact host DOCKER-USER rules and verified-FD-pinned per-netns INPUT/OUTPUT/FORWARD default deny. Allow only client-to-target TLS5432 tuples and stateful replies; no Docker DNS, gateway, loopback or general egress. Use named certificates plus pinned PGHOSTADDR, not DNS. Permanent IPv6 neighbors keep positive private TLS working without permitting NDP forwarding.
7. Using the exact final client image, prove IPv4 and IPv6 private TLS, wrong hostname and wrong CA rejection, actual numeric productionHTTPS443/directDB5432 and IPv6 denial, DockerDNS UDP/TCP denial and gateway/loopback denial. Verify exact rule readback before and after. Native source/target identities, PG170006, no Unix sockets, no shared/session/local preloads, cronoff, no unexpected workers or other client connections, zero ordinary target rows and full census coverage are mandatory. A nonzero connection exit alone is insufficient.
8. Independently review and bind the actual fresh target plan/evidence before payload unlock. This must be a real review/control binding, not the setup script asserting `independentlyReviewed=true`. The original engine requires fresh evidence within15minutes; a stale review cannot be refreshed by editing timestamps. Bind fresh private host/IP/port/database/systemIdentifier, exact server image digest, exact final client image/tool evidence, network evidence hash, complete baseline pins, reviewed source SHA, and approved target-only operator role. No prior destroyed target identity can satisfy this gate.
9. Only after that gate may the host atomically create a0600 phrase file in the already-owned private input directory, readable by the nonroot restore client through its read-only bind. The existing protected backup passphrase supplies this file; never use a workflow input, command argument, Docker Config.Env, artifact or log. A minimal reviewed Python launcher reads the private file into a local `env` dictionary passed to the existing engine; it does not propagate the phrase to subprocess environments. Existing engine GPG transport remains private stdin with its own temporary GNUPGHOME.
10. Execute the unchanged restore engine against the fresh pinned target under the required outer hard timeout. Recheck current attestation immediately before decrypt, before first schema write, and before row import, as the engine already requires. Do not weaken its original destination guard, TLS, source-project, private-host, passfile, complete TOC, owner/ACL, bounded archive, role or postcondition checks.
11. Publish only the fixed safe restore result and sanitized source/target/tool/network hash-count receipts. No catalog, DDL, row hashes, private metadata, target database, raw diagnostics, plaintext, passphrase, TLS private keys or unencrypted Docker backing files are uploaded. The encrypted source backup remains under its existing approved seven-day artifact policy. Network guards remain in place if any cleanup/daemon state is uncertain. Never remove guards merely because `docker inspect` exited1.

## Existing engine invocation contract

The launcher must supply only these private environment bindings (plus its ordinary tool PATH/locale/CA policy):

| Binding                                         | Required value                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------- |
| KOVA_AUTH_RECOVERY_CONFIRMATION                 | RESTORE_EMPTY_ISOLATED                                              |
| KOVA_AUTH_RESTORE_BASELINE_MODE                 | empty-database                                                      |
| KOVA_AUTH_BACKUP_ENCRYPTED_SHA256               | exact reviewed ciphertext SHA-256                                   |
| KOVA_APPROVED_BACKUP_SOURCE_SHA                 | exact source SHA inside the capture envelope                        |
| KOVA_PRODUCTION_BACKUP_PASSPHRASE               | existing protected value loaded privately after qualification       |
| APPROVED_ISOLATED_PG17_DATABASE_URL             | passwordless named private URI with verify-full and private CA path |
| APPROVED_ISOLATED_HOST / DBNAME / PORT          | exact reviewed fresh target                                         |
| APPROVED_ISOLATED_SERVER_IP / SYSTEM_IDENTIFIER | actual native fresh target address/cluster                          |
| PGPASSFILE                                      | target-only owned regular0600 file, never PGPASSWORD                |
| KOVA_AUTH_RESTORE_ATTESTATION / SHA256          | exact private independently reviewed fresh evidence file/hash       |

The approved real invocation remains:

```text
timeout --signal=TERM --kill-after=10s 26m python3 scripts/release/managed-auth-recovery.py restore --execute --archive /run/restore-input/managed-auth-backup.tar.gpg --output /run/restore-output/managed-auth-restore-receipt.json
```

A file-loading launcher may call the same module's restore API with the same contract so the passphrase need not be embedded in Docker's stored container environment. It must preserve signal handling, stage selection, umask, bounded_operation deadline and all existing checks. The output bind contains only a success receipt; plaintext workspace is separate and never uploaded.

## Recovery acceptance and cleanup boundary

Database recovery is proved only by actual table/matview row fingerprints, sequence values/called flags, large objects, full schema hash including owners/policies/privileges, roles and exact TOC coverage. A failed schema/data/postcheck never triggers blind replay or production fallback. Keep the owned target quarantined with egress guards for evidence-backed review, or destroy it only under an explicitly approved cleanup policy. Do not turn a failed restore into a success by changing the expected hashes.

Even a success must retain existing `providerConfigRecoveryQualified=false`, `credentialCustodyQualified=false`, `storageObjectBytesRecovered=false`, `fullProjectRecoveryQualified=false` until those separate scopes have actual evidence. Existing-account login adoption and owned Auth acceptance are additional production tests; a database rehearsal does not establish them.
