# Search, images, shopping, and local discovery

Source implementation is available at `/discovery` and `/maps` (Local places). Live discovery remains disabled until the existing Firecrawl configuration, database migration, reviewed request caps, and owner activation are present. No provider was called, account purchased, deployment changed, or commercial price inferred during implementation.

The authenticated API uses the existing Firecrawl Cloud `/v2/search` and `/v2/scrape` endpoints. It makes one provider request for each explicit user action, with no automatic retry, six search results, a 20-second response deadline, and a 256-KiB response ceiling. Search input is limited to 300 characters plus an optional 160-character manually entered place. API requests reject client provider settings, arbitrary scrape URLs, and client pricing. Responses are untrusted source reports, not instructions or independently confirmed facts.

- Web results show title, source, snippet, link, and retrieval time. Empty, blocked, malformed, oversized, cancelled, or unavailable responses have explicit recovery states. Users refine the text and search mode without an automatic provider call.
- Image search returns source-page and image URL metadata. It does not fetch image bytes on display. Each image requires a separate user click explaining that its host will be contacted. The browser image uses anonymous CORS and no referrer; hosts that disallow that load show an explicit failure and source-page handoff. Navigation uses HTTPS public hostnames, excludes credentials, IP literals, local suffixes and alternate ports, and uses `noopener noreferrer`. This is an explicit external-image load, not a KovaGPT image proxy.
- Shopping initially shows source links with unknown merchant price and stock. “Check merchant details” uses a 15-minute owner-bound HMAC source token issued only for an accepted shopping search result. It requests deterministic `product` extraction with `maxAge: 0`, no actions and no document parser. A provider HTTP 200 does not validate the target: the page status must succeed, and source/product canonical origins must match the original merchant. Ambiguous extraction remains unknown. Each returned variant retains its own merchant ID, SKU, option values, currency, amount, boolean stock observation and check time. No missing currency or stock state is inferred from snippets. Up to four exact variants can be compared without converting currencies or claiming a guaranteed checkout price, shipping, tax, availability, or product equivalence.
- Local discovery requires a place entered manually. It has no browser geolocation or background location access. Results are sourced web links, with explicit Google Maps query and merchant/reservation-site handoffs. It does not claim a licensed native map, geocoded distance, opening hours, weather feed, live table availability, or an in-app reservation.
- Image/product matching is text-guided. Users can ask chat to describe a photo and paste that description into search. It does not send a photo to search or claim reverse-image or exact visual matching.

## Admission, deletion, and retention

`KOVA_DISCOVERY_ENABLED=false` is the default. Readiness also requires `FIRECRAWL_API_KEY`, a separate server `KOVA_DISCOVERY_SOURCE_SECRET` of 32–512 characters, and explicit positive `KOVA_DISCOVERY_GLOBAL_DAILY_REQUESTS` and `KOVA_DISCOVERY_USER_DAILY_REQUESTS`. The global limit is at most 100,000 requests per UTC day; the user limit is at most 1,000. These are validation maxima, not recommended operating allowances. `KOVA_GENERATION_DISABLED=true` also disables discovery. Actual positive allowances must be reviewed against the operator's provider plan and budget before activation. Request counts are not monetary cost, pricing or margin guarantees.

`admit_discovery_request` takes the canonical account lock, checks current owner existence through the narrow private Auth helper (without granting `service_role` Auth table SELECT), deletion fence, ban, and Lockdown. It serializes the global UTC-day row and atomically consumes both global and personal counters. Failure, cancellation, or a lost response never refunds an admitted provider attempt. Client roles have no table or function access. An admission immediately precedes transport; cancellation before transport prevents the call. The system cannot undo a request already sent to the provider.

Only request counts are persisted, never queries, places, source tokens, image bytes, or merchant results. The personal count-only export view is registered in account export and cascades with Auth deletion; global aggregate counts survive account deletion so deleting accounts cannot refund the shared cap. Counts older than seven days are purged in bounded batches during admission and through the existing authenticated developer-billing maintenance worker, which runs independently of feature activation. Scheduled worker execution is still an operator deployment requirement; cleanup is eventual when that worker runs, not a claim that local source schedules itself.

The browser keeps result and comparison state only in memory and remounts on principal changes or a device privacy reset. Session acquisition, transport and browser response parsing have cancellation deadlines and a 128-KiB response cap. Every authenticated request pins the expected user; unmount cancels requests and late responses cannot restore another user's state. Loading third-party content or following an external link is a deliberate user action.
