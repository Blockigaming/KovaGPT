# Isolated Python and CSV executor

`createWorkSandboxExecutor({ enginePath: "/usr/bin/docker", image })` exposes `probe()`, `run(job, { signal })`, and `reapExpired()`. The final image must use an immutable `@sha256:` reference or local `sha256:` image ID already installed on the approved runner host. Docker's `runsc` runtime is required; there is no host-Python, ordinary-container, remote-daemon, or image-pull fallback. Startup readiness must use `probe()` and a fresh authenticated backend check before admitting Work jobs.

The runner passes `{ jobId, code, inputFiles: [{ name, bytes }], timeoutMs, maxOutputBytes }`. `run` returns `{ stdout, stderr, exitCode, outputs: [{ name, bytes }] }` only after exact-container cleanup succeeds. Work must independently hash the returned bytes and bind them to its existing run/owner/epoch/step/input-hash receipt before publishing an artifact. Nonzero exit codes are failed code runs, not completed Work outputs. The executor does not send messages, access credentials, invoke AI providers, or publish files.

Code uses Python's standard library, including `csv`, `json`, `math`, `statistics`, and `sqlite3`. Files are available by their simple names in `os.environ["KOVA_INPUT_DIR"]`; write deliverables into `os.environ["KOVA_OUTPUT_DIR"]`. Nested paths, symlinks, hardlinks, directories, and special output files are rejected. No package installation or external network is available. Each run has a new directory inside its private tmpfs; no input or output data is mounted from, extracted to, or executed on the host. Input files are initialized with read-only permissions, but generated code can manipulate its own disposable sandbox data; original source authority and hashes remain in Work's service-owned record.

Limits are 64 KiB code, 16 input files totaling 8 MiB, 16 output files totaling at most 8 MiB, 64 KiB each of stdout/stderr, and at most 30 seconds elapsed. Containers run as UID/GID 65532 with a read-only root, no network, dropped capabilities, no new privileges, private cgroups, a 32-process limit, one CPU, 256 MiB memory with no extra swap, bounded file descriptors/file size/CPU time, and bounded noexec tmpfs filesystems. Logs do not persist through Docker's logging driver. The host also bounds every CLI pipe and timer.

Caller abort and timeout kill the attached CLI and send an independent force-removal request for the random container name. The create/start split ensures an uncertain late create receives no code. Expiring labels support bounded restart recovery via `reapExpired()`; the service should run this before accepting work and periodically afterward. Cleanup failure is an error even if output was produced. Cleanup failure quarantines this executor: readiness and new admission remain unavailable until exact-container recovery succeeds. The trusted runner host must monitor cleanup failures and resource health.

The Dockerfile pins the official Python 3.13 slim Bookworm manifest retrieved from Docker Hub on September 5, 2026. Build using this directory as the context; an approved `PYTHON_BASE_IMAGE` override must also use SHA-256. Deploy the resulting image by its final immutable digest. No external dependency installation is needed. Verify the configured `runsc` implementation and Docker cgroup enforcement on that host.

Run the real acceptance gate there with `KOVA_WORK_SANDBOX_IMAGE` set to that digest and `node work-runner/sandbox-image/acceptance.mjs --execute`. It checks actual CSV output bytes, non-root identity, read-only root, denied external network, forbidden output types, deadline termination, and cleanup. The dedicated `Work Sandbox Isolation` GitHub Actions workflow performs this real gate automatically on an ephemeral Ubuntu runner. It verifies the official gVisor 20260831.0 full bundle against its pinned SHA-512, configures that temporary runner only, builds the pinned source image, runs acceptance, and removes its test containers. This hosted gate is part of autonomous CI, not an owner action. Production activation remains a separate deployment decision.

The Node tests use an injected CLI process to verify argument boundaries, admission, output limits, cancellation, and recovery; they do not claim that a sandbox runtime is installed. This source package does not deploy a container or activate a provider.

The isolation contract follows the official [Docker container run options](https://docs.docker.com/reference/cli/docker/container/run/) and [gVisor Docker configuration](https://gvisor.dev/docs/user_guide/quick_start/docker/). The runtime protects against untrusted code; Python-level checks are validation, not a sandbox.
